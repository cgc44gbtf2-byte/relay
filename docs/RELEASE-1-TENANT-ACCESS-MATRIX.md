# Release 1 tenant access reconciliation

Scope: authenticated HTTP resources from the original tenant-isolation checklist. Route paths below are relative to `/api`; `:communityId` is the workspace boundary. The negative matrix in `artifacts/api-server/src/admin.test.ts` ("rejects valid resource IDs from another workspace on reads and writes") constructs *two real workspaces with the same manager* and substitutes IDs across them. Its positive controls establish that the records actually exist and can be read in their own workspace. This is stronger than a denial produced merely because the caller has no permissions anywhere. A separate test covers audience separation *within* a workspace. This is not an audit of WebSocket event delivery, storage-provider policies, or production data.

| Resource / endpoints | Ownership and access chain | Negative read/write evidence |
| --- | --- | --- |
| Workspace detail `GET /communities/:communityId`, list `GET /communities`, dashboard/activity `GET /communities/:communityId/{dashboard,activity}` | List restricts to memberships/privileged access; detail calls `canAccessBusiness` and separately filters channel, document, announcement and employee collections. Dashboard and activity require workspace-scoped permissions. | Foreign rows absent in detail/document lists; private workspace and activity tests in `admin.test.ts`. |
| Tasks `GET, PATCH /communities/:communityId/tasks/:taskId`; `POST .../tasks`, `.../comments`, `.../attachments`; `GET .../attachments/:attachmentId` | Workspace permission + task ID paired with community ID; attachments must belong to the checked task. Creation validates department/location relationships in the same workspace. | Foreign task read, patch, comment, attachment write/read, mismatched attachment, and foreign department/location cases. |
| Documents `GET, POST /communities/:communityId/documents`; `POST .../document-folders`, `.../documents/:documentId/{versions,acknowledge,permissions}`; `GET .../documents/:documentId/download/:versionId` | `documentForUser` checks document ID + community ID and membership/visibility; manager writes check workspace permission, document pairing, and recipient/folder scope. Download also requires version ID + document ID (an ID-only version lookup would not suffice). | Foreign document excluded from list; foreign/mismatched version download, foreign version write/ack/permissions and foreign recipient/folder rejection. Own version download/write positive controls. |
| Invitations `POST /communities/:communityId/invitations`, `.../accept`, `.../decline`, `.../:invitationId/{revoke,resend}`; invitations in workspace detail | Manager-scoped creation/revoke/resend; token hash **and** community ID on accept/decline with verified recipient email; organization assignments checked against target workspace. | Foreign invitations excluded from detail; token accept/decline, ID revoke/resend, and foreign organization assignments denied; source invitation remains pending. |
| Organization `POST /communities/:communityId/{departments,locations,teams}`; `PATCH .../{departments,locations,teams}/:unitId/manager`, `.../employees/:employeeId`, `.../employees/:employeeId/organization`; `PUT, DELETE .../teams/:teamId/members/:memberId` | Workspace manager permission, persisted unit/member pairing with community, same-community manager, department, location and team references. | Foreign employee/profile, unit manager, team membership and relationship IDs denied, including foreign employee as manager or team member; original profile remains unchanged. |
| Policies `POST /communities/:communityId/policies`, `POST .../policies/:policyId/acknowledge`; collection in detail | Workspace permission for creation; policy ID + workspace pairing and membership for acknowledgement; detail scoped to community. | Foreign policy absent from detail and acknowledgement denied; own acknowledgement positive control. |
| Announcements `POST /communities/:communityId/announcements`, `DELETE .../:announcementId`, `POST .../:announcementId/{read,acknowledge,attachments}`, `GET .../attachments/:attachmentId`; `GET /announcements` | Creator's permission is scoped to workspace; audience relationship IDs and recipient validated in workspace. ID routes pair announcement with workspace and attachment with announcement; read/acknowledge/attachment downloads also check the member's audience (with manager/author access). Detail filters audience; global feed applies membership + audience + schedule/expiry (platform admins retain privileged feed access). Immediate and both due-activation paths intersect current workspace membership and require active team membership. | Foreign announcement absent from detail; foreign read/ack/delete/attachment and mismatched attachment denied; foreign audience IDs rejected. Target/bystander test proves feed, read/acknowledgement/attachment denial, scheduled notification separation and expiration; revoked team access and removed workspace membership are denied after activation through both paths. |
| Scoped assignments `POST /admin/role-assignments`; community member role `PATCH /communities/:communityId/members/:memberId/role`; assignments in workspace detail | Grant permission and scope validation enforce workspace/category/channel/department relationship and member pairing; detail restricts rows to workspace and permission. | Foreign category/channel/department grants and foreign member role denied; no foreign grants persisted; valid same-workspace grant succeeds. |
| Channel/category/message `GET, POST, PATCH, DELETE /channels...`, `/messages...`; `POST, PATCH, DELETE /communities/:communityId/channels...`, `/categories...` | Channel access helpers enforce membership/role and channel's workspace; mutations verify category/channel pairing; message routes resolve parent channel/DM and check access, not just message ID. | Category and channel cross-workspace tests in `admin.test.ts`; channel-access tests and moderation/revocation suites. These are not claims of exhaustive realtime delivery verification. |
| Notifications `GET /notifications`, `GET /notifications/:id/detail`, `POST /notifications/{:id/read,:id/archive,:id/restore,read-all}`, `DELETE /notifications/{:id,clear}` | Personal collection/read/update/delete keyed by authenticated user; detail resolves linked message only after DM participant or channel read check. | Notification owner tests in `admin.test.ts`; message/channel read checks in `irc.ts`. No workspace ID is accepted on these routes. |

An ID-only lookup is not automatically a defect: the authorization boundary is the complete chain *before bytes are returned or a write is committed*. The announcement feed was a verified exception: membership alone did not enforce audience. The fix and regression above address it. Remaining Release 1 work outside this matrix remains listed in `RELEASE-1-AUDIT-STATUS.md`; a passing local database test is not a production sign-off.
